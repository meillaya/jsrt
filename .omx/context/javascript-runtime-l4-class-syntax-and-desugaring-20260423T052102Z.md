# Context Snapshot — JavaScript Runtime L4 class syntax and desugaring/direct support

- task statement: Create the L4 consensus plan for jsrt after the completed L3 milestone.
- desired outcome: Produce approved L4 PRD + test spec artifacts for the next milestone, grounded in the current L3-capable runtime and the roadmap's L4 objective.
- known facts/evidence:
  - Roadmap L4 is `class syntax and desugaring/direct support`, high risk, recommended execution mode `team`.
  - Current baseline supports prototype chains, `this`, parenthesized `new`, narrow function `prototype`, and rejects classes / super.
  - The existing `prd-javascript-runtime-milestone-4.md` and matching test spec are stale early-project docs about loops/logical operators, not the roadmap L4 milestone.
  - The L3 PRD explicitly positioned the current constructor/prototype runtime as the substrate for future class lowering.
- constraints:
  - Plan only; do not implement L4 here.
  - Respect current L3 semantics and keep the plan consistent with existing parser/evaluator/compiler/VM architecture.
  - The plan must be consensus-reviewed and save canonical artifacts under `.omx/plans/`.
- unknowns/open questions:
  - Whether L4 should prefer pure desugaring, direct runtime support, or a hybrid.
  - Exact bounded class surface for the first L4 landing (extends/super/static/computed names/expressions).
  - How much of the class feature set should be staged within L4 vs explicitly deferred.
- likely codebase touchpoints:
  - `include/jsrt/{token.h,ast.h,bytecode.h,value.h}`
  - `src/{lexer.c,parser.c,ast.c,eval.c,compiler.c,vm.c,bytecode.c}`
